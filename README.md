# Buyer Assistant (C++17)

Консольное приложение для подбора комплекта мебели по диалогу на русском языке.
Это самостоятельная C++-реализация хакатонного кейса `K0STYAa/sfedu-hackathon-buyer-assistant`:
исходный репозиторий содержит контракт, схемы и примеры, но не готовую программу.

Программа читает один JSON-запрос из `stdin`, разбирает условия покупки, ищет
подходящие комплекты в локальном каталоге и выводит в `stdout` один JSON-ответ
со статусом `ok`, `clarify` или `no_match`. Все служебные сообщения и логи идут
только в `stderr`.

## Быстрый старт (Windows)

```bat
call "C:\Program Files (x86)\Microsoft Visual Studio\2022\BuildTools\Common7\Tools\VsDevCmd.bat" -arch=x64 -host_arch=x64
cmake -S . -B build -G "NMake Makefiles" -DCMAKE_BUILD_TYPE=Release -DBA_BUILD_TESTS=ON
cmake --build build
ctest --test-dir build --output-on-failure
```

Запуск публичного примера:

```bat
build\run.exe --catalog data\catalog.json --no-llm < examples\01-selection\request.json
```

Или через обёртку, которая сама подставляет каталог:

```bat
run.cmd < examples\01-selection\request.json
```

Пример ответа (конкретные `listing_ids` зависят от каталога; важен любой
корректный набор):

```json
{
  "options": [
    {
      "explanation": "Комплект: стол шириной 100 см, кресло с регулировкой высоты и лампа 5 000 К. Итого 4 900 ₽.",
      "listing_ids": ["demo-1-1-10", "demo-1-2-05", "demo-1-3-04"],
      "total_rub": 4900
    }
  ],
  "status": "ok"
}
```

## Контракт

### Вход

Объект JSON с единственным полем `messages` — массивом от 1 до 20 сообщений:

```json
{
  "messages": [
    { "role": "user", "text": "Нужны стол и кресло" },
    { "role": "assistant", "text": "В каком городе искать?" },
    { "role": "user", "text": "Таганрог, до 15 000 рублей" }
  ]
}
```

Правила проверки:

- роли чередуются, начиная с `user`; последнее сообщение — от `user`;
- `role` — только `user` или `assistant`;
- `text` — непустая строка;
- неизвестные поля запроса и сообщений отклоняются;
- размер входа ограничен `app.maxInputBytes` (по умолчанию 1 МиБ).

Нарушение любого правила — ошибка входа, код возврата `3`.

### Выход

Ровно один из трёх вариантов.

`ok` — найден хотя бы один комплект:

```json
{
  "status": "ok",
  "options": [
    {
      "listing_ids": ["t12", "c04", "l09"],
      "total_rub": 12200,
      "explanation": "Комплект: ... Итого 12 200 ₽."
    }
  ]
}
```

- от 1 до 3 вариантов (ограничение `app.maxOptions`);
- в каждом варианте ровно по одному объявлению на каждую запрошенную категорию;
- все объявления из одного города;
- `total_rub` — точная сумма цен, не больше бюджета (граница включительная);
- варианты отсортированы от дешёвого к дорогому;
- `explanation` строится только из структурированных атрибутов, без названий
  и описаний товаров.

`clarify` — не хватает обязательных условий:

```json
{
  "status": "clarify",
  "questions": [
    { "field": "budget_rub", "text": "Какой у вас бюджет на весь комплект?" }
  ]
}
```

Поля вопросов: только `budget_rub`, `city_id`, `categories`, каждое не более
одного раза. Неизвестный город или неподдерживаемая категория тоже приводят к
уточняющему вопросу.

`no_match` — условия понятны, но подходящих комплектов нет:

```json
{
  "status": "no_match",
  "message": "В городе Таганрог нет столов."
}
```

В `no_match` нет идентификаторов объявлений и вопросов. Сообщение объясняет
причину: отсутствие категории в городе, невозможное ограничение по атрибуту
или нехватку бюджета до самого дешёвого комплекта.

## Возможности

### Детерминированный разбор русского текста

Разбор не зависит от языковой модели и работает всегда:

- **Города** — названия и идентификаторы из `cities.json`, с учётом падежных
  окончаний (`Таганрог`, `Таганроге`, `Ростове-на-Дону`, `Азов`). Неизвестные
  города (`Москва`, `Казань`, ...) распознаются как неподдерживаемые.
- **Категории** — стол, кресло, лампа и синонимы (`стул`, `светильник`, `торшер`).
  Неподдерживаемые предметы (`диван`, `шкаф`, `кровать`, ...) вызывают уточнение.
- **Отрицание и замена** — `не нужен стол, нужно кресло`, `без стола`,
  `уберите лампу`, `вместо стола кресло`. Отрицание не перетекает через запятую
  и границу предложения; `Стол не шире метра` — это ограничение, а не отказ от
  стола.
- **Диалог** — условия накапливаются между сообщениями, последнее явное значение
  побеждает; поддерживаются исправление города и категорий, замена набора после
  уточнения и добавление категорий (`ещё кресло`).
- **Бюджет** — `15 000 ₽`, `15000`, `15 тыс`, `20к`, `пятнадцать тысяч`,
  `10-15 тысяч`, `до 20000 рублей`. Диапазон берёт верхнюю границу; два разных
  бюджета без диапазона помечаются как неоднозначные.
- **Ширина стола** — `не шире 80 см`, `до метра`, `шире 80 см`, `уже 90 см`,
  `от 70 до 90 см`. Метр переводится в 100 см.
- **Цветовая температура лампы** — `4000 К`, `4000 кельвин`, `от 3000 до 4000`,
  `температура света 3000`.
- **Регулировка высоты кресла** — `с регулировкой высоты`, `без регулировки`,
  `высота не регулируется`.
- **Сброс ограничений** — `ширина стола не важна`, `цветовая температура не
  принципиальна`, `регулировка высоты не важна`.

Если для запрошенной категории задано ограничение по атрибуту, объявления без
этого атрибута не подходят. Это соответствует правилу кейса: отсутствующий
атрибут не считается удовлетворяющим условию.

### Подбор

- Поиск идёт только по структурированным полям каталога.
- Город и категории обязательны; бюджет обязателен.
- Для каждой запрошенной категории перебираются подходящие объявления, затем
  собираются комплекты; лишние категории в комплект не добавляются.
- Варианты сортируются по сумме, затем по идентификаторам — результат
  детерминирован.
- Названия и описания объявлений не участвуют в принятии решений и не попадают
  в ответ.

### Необязательная LLM

Языковая модель — вспомогательный источник недостающих условий, а не замена
детерминированному разбору. Она включается только при наличии API-ключа и
только в режимах `auto` или `always`.

Модель получает:

- системную инструкцию с правилами;
- очищенный текст диалога (служебные символы удалены);
- списки допустимых идентификаторов городов и категорий.

Модель **не получает** названия, описания, цены и другие поля каталога.
Ответ модели проверяется по строгой JSON-схеме: неизвестный город, категория,
тип или значение вне диапазона — техническая ошибка.

Слияние результатов:

- явно разобранные детерминированные факты никогда не перезаписываются;
- модель может заполнить только отсутствующий город, бюджет или категории;
- атрибуты (ширина, температура, регулировка) принимаются от модели только
  тогда, когда в тексте есть явная подсказка о соответствующем ограничении;
- неоднозначные и некорректные условия модели не исправляются: пользователю
  задаётся уточняющий вопрос.

Текст диалога рассматривается как данные. Инструкции вида «игнорируй правила»
не влияют на схему ответа и не могут изменить каталог или решения программы.

## Сборка

### Windows, MSVC (проверено)

Проверено на MSVC 14.44 (Visual Studio 2022 Build Tools) и CMake 4.4.
Генератор NMake надёжно работает в окружении Build Tools:

```bat
call "C:\Program Files (x86)\Microsoft Visual Studio\2022\BuildTools\Common7\Tools\VsDevCmd.bat" -arch=x64 -host_arch=x64
cmake -S . -B build -G "NMake Makefiles" -DCMAKE_BUILD_TYPE=Release -DBA_BUILD_TESTS=ON
cmake --build build
```

Готовый бинарник: `build\run.exe`. Цель CMake называется
`buyer_assistant`, но исполняемый файл — `run.exe`.

Если используется полная Visual Studio с рабочей установкой Windows SDK,
подойдёт и обычный генератор Visual Studio:

```bat
cmake -S . -B build -A x64 -DCMAKE_BUILD_TYPE=Release
cmake --build build --config Release
```

## Запуск

```
run --catalog PATH [параметры]
```

Обязателен только `--catalog`. Запрос читается из `stdin`, ответ пишется в
`stdout`.

| Параметр | Назначение |
|---|---|
| `--catalog PATH` | путь к JSON-каталогу (обязательно) |
| `--config PATH` | путь к JSON-конфигурации |
| `--no-llm` | не обращаться к модели, даже если ключ задан |
| `--dump-requirements` | вывести разобранные условия в `stderr` |
| `--log-level LEVEL` | `error`, `warn`, `info` или `debug` |
| `--help`, `-h` | справка |
| `--version` | версия |

Допустимы формы `--catalog=path` и `--config=path`.

Если `--config` не указан, программа ищет `config.json` в текущем каталоге, а
затем рядом с исполняемым файлом (Windows). Если файла нет, используются
значения по умолчанию и переменные окружения. Отсутствие `config.json` — не
ошибка.

Обёртки:

- `run` — Linux/macOS: исполняемый скрипт в корне репозитория, подставляет
  `--catalog data/catalog.json`; при первом запуске на Unix выполните
  `chmod +x run`;
- `run.cmd` — Windows: подставляет `--catalog data\catalog.json`.

Обе обёртки запускают уже собранный `build/run`. Дополнительные аргументы
передаются программе, поэтому обёртку можно использовать и с `--config`,
`--log-level` и т.д.

## Конфигурация

Пример — `config.example.json`. Все поля необязательны; неизвестные поля,
неверные типы и значения вне диапазонов отклоняются с кодом `3`.

```json
{
  "llm": {
    "mode": "auto",
    "baseUrl": "https://sfedu-hackathon-ai-gateway.sfedu-hackathon-ai-gateway.workers.dev/v1",
    "model": "google/gemma-4-31B-it",
    "apiKey": "",
    "userAgent": "buyer-assistant/1.0",
    "timeoutSeconds": 20,
    "maxTokens": 512,
    "temperature": 0.0,
    "maxRetries": 1,
    "required": false
  },
  "app": {
    "maxOptions": 3,
    "maxInputBytes": 1048576,
    "logLevel": "info"
  }
}
```

| Поле | Допустимые значения | По умолчанию |
|---|---|---|
| `llm.mode` | `off`, `auto`, `always` (алиасы: `none`, `disabled`, `on`, `required`) | `auto` |
| `llm.baseUrl` | `http://` или `https://`, без пробелов | шлюз кейса |
| `llm.model` | непустая строка | `google/gemma-4-31B-it` |
| `llm.apiKey` | строка; пустая означает «ключа нет» | пусто |
| `llm.userAgent` | непустая строка | `buyer-assistant/1.0` |
| `llm.timeoutSeconds` | 1–90 | 20 |
| `llm.maxTokens` | 1–2000 | 512 |
| `llm.temperature` | 0.0–2.0 | 0.0 |
| `llm.maxRetries` | 0–5 | 1 |
| `llm.required` | `true`/`false` | `false` |
| `app.maxOptions` | 1–3 | 3 |
| `app.maxInputBytes` | 1024–67108864 | 1048576 |
| `app.logLevel` | `error`, `warn`, `info`, `debug` | `info` |

Переменные окружения переопределяют файл: `LLM_BASE_URL`, `LLM_MODEL`,
`LLM_API_KEY`, `LLM_USER_AGENT`. Пустые значения игнорируются.

### Режимы LLM

- `off` — модель не вызывается.
- `auto` — модель вызывается только если есть ключ и детерминированный разбор
  чего-то не хватает (город, бюджет, категории) или в диалоге есть расплывчатые
  пожелания. Без ключа поведение полностью детерминированное, ошибки нет.
- `always` — модель вызывается на каждом запросе; требует непустой ключ, иначе
  программа завершается с ошибкой конфигурации до чтения запроса.

`llm.required=true` вместе с `auto` или `always` также требует ключ на старте.

Ключ никогда не выводится в логах: `DescribeConfig` заменяет его на
`apiKeyConfigured: true/false`.

## Данные

```
data/catalog.json      111 объявлений: 3 города × 3 категории
data/cities.json       справочник городов
data/categories.json   справочник категорий
schemas/               JSON-схемы запроса, ответа и справочников
examples/              публичные примеры кейса
docs/                  контракт и описание LLM API из кейса
```

Справочники городов и категорий загружаются из файлов `cities.json` и
`categories.json` рядом с каталогом. Если файлов нет, используются встроенные
Таганрог, Ростов-на-Дону, Азов и три категории. Это позволяет заменить каталог
и справочники, не пересобирая программу.

Каталог проверяется строго:

- массив не длиннее 250 объявлений;
- уникальные `id`, непустые `title`;
- `price_rub` — целое положительное число;
- известная категория и известный город;
- известные атрибуты имеют правильный тип;
- вложенные объекты и неизвестные поля верхнего уровня запрещены.

Объявление с `"attributes": {}` допустимо, но не подходит под ограничения по
атрибутам.

## Архитектура

```
include/ba/            публичные заголовки
src/
  main.cpp             CLI, чтение stdin, вывод ответа, коды возврата
  app/Application.cpp  валидация запроса, диалог, вызов LLM, решение
  core/
    MessageInterpreter.cpp  детерминированный разбор русского текста
    DialogueAnalyzer.cpp    накопление и замена условий между сообщениями
    Catalog.cpp             загрузка и валидация каталога
    Directories.cpp         загрузка справочников
    BundleSearch.cpp        поиск и диагностика комплектов
    DecisionEngine.cpp      ok/clarify/no_match и объяснения
  models/              категории, объявления, условия, ответы
  services/
    Config.cpp         конфигурация и валидация
    LlmClient.cpp      HTTP-клиент OpenAI-совместимого API
    LlmExtractor.cpp   схема, извлечение и слияние фактов
    WinHttpTransport.cpp / CurlHttpTransport.cpp
  utils/               UTF-8, JSON, логирование, ошибки
tests/                 138 модульных тестов и CLI-интеграция
```

Поток обработки:

1. `Application::ParseMessages` проверяет форму запроса.
2. `DialogueAnalyzer` прогоняет сообщения пользователя через
   `MessageInterpreter` и накапливает условия.
3. При необходимости `LlmExtractor` дополняет отсутствующие факты.
4. `DecisionEngine` задаёт вопросы, ищет комплекты или объясняет отказ.
5. `Response::ToJson` формирует точную форму ответа.

## Тесты

```bat
ctest --test-dir build --output-on-failure
```

Или напрямую:

```bat
build\tests\ba_tests.exe
```

138 модульных тестов покрывают:

- нормализацию UTF-8, падежи городов, отрицание и границы предложений;
- бюджеты, диапазоны, `20к`, `тыс`, количество и ширину;
- диалог: накопление, замена, сброс атрибутов, исправление ошибок;
- загрузку и валидацию каталога, справочников, конфигурации;
- поиск: границы inclusive/exclusive, отсутствующие атрибуты, бюджет, лимит
  вариантов, диагностику;
- решения `ok`/`clarify`/`no_match` и точные формы JSON;
- LLM-клиент: заголовки, лимиты, повторы, коды ошибок, схемы, слияние фактов;
- приложение целиком: публичные примеры, LLM, отсутствие ключа, ошибки;
- CLI: аргументы, справку, коды возврата.

`ctest` дополнительно запускает `tests/cli_tests.cmake`: проверяет коды
возврата, оба публичных примера, ограничения по городу/категории/бюджету,
точность сумм, отсутствие идентификаторов в `no_match` и вывод
`--dump-requirements` только в `stderr`.

## Коды возврата

| Код | Значение |
|---|---|
| `0` | ответ сформирован (`ok`, `clarify` или `no_match`) |
| `1` | внутренняя ошибка |
| `2` | ошибка аргументов командной строки |
| `3` | ошибка входа, конфигурации или каталога |
| `4` | ошибка внешнего сервиса (LLM) |

`no_match` — не ошибка: код `0`, как и у остальных статусов.

## Безопасность и приватность

- Сетевые запросы выполняются только при включённой LLM и заданном ключе.
- Ключ хранится в конфигурации или переменной окружения, в логи не попадает.
- Названия, описания и цены каталога не отправляются модели.
- Ответ модели валидируется по схеме и допустимым значениям.
- Размеры запроса и ответа ограничены; HTTP-редиректы отключены; таймауты
  заданы; заголовки проверяются на переводы строк.
- API-ключ не записывается в репозиторий: `config.example.json` содержит
  пустое значение.

## Ограничения

- Русский язык; три категории и три города в демонстрационных данных.
- Цены — целые рубли; валюта не конвертируется.
- Каталог локальный, без сети и без динамического обновления.
- LLM не является обязательной и не влияет на детерминированные факты.
- Программа не хранит историю между запусками: диалог передаётся целиком в
  запросе.

## Решения по реализации

- Детерминированный разбор — основной и всегда доступный. LLM только дополняет
  отсутствующие условия.
- Ограничение по атрибуту требует наличия атрибута: `{}` не удовлетворяет
  условию.
- Для публичного примера 01 достаточно любого корректного набора вариантов;
  пример 02 обязан спросить только `budget_rub`.
- Ошибка LLM считается технической (код `4`), если вызов действительно
  выполнялся. В режиме `auto` без ключа вызова нет, поэтому ошибки тоже нет.
- CMake-цель называется `buyer_assistant`, а бинарник — `run`, чтобы совпадать
  с ожиданиями кейса.

## Диагностика

- **`LNK1104: cannot open file "ucrtd.lib"`** — используйте проверенную
  команду с NMake из `VsDevCmd.bat` (см. выше) или запускайте сборку из
  «x64 Native Tools Command Prompt for VS 2022».
- **Кракозябры в консоли** — программа включает UTF-8 для консоли Windows.
  В PowerShell при необходимости выполните
  `[Console]::OutputEncoding = [Text.Encoding]::UTF8`.
- **Нужно увидеть разобранные условия** — добавьте `--dump-requirements`:
  JSON условий будет в `stderr`, ответ в `stdout` останется чистым.
- **Ошибка LLM** — проверьте ключ и `llm.baseUrl`; для проверки без сети
  используйте `--no-llm`.
- **`clarify` вместо `ok`** — программа намеренно спрашивает недостающие
  обязательные условия: город, категории и бюджет.
